# Viora Online — Supabase setup (PRE-RELEASE)

**Status:** backend deployment and live end-to-end tests are REQUIRED before public distribution. This feature lives in `feature/v1.4-online-accounts-supabase`, separate from the working v1.4 Workspaces Lite branch. Viora Manager is unchanged.

## 1. Create a free Supabase project

1. Open https://supabase.com/dashboard and create a project in your own account.
2. Under Authentication → Providers → Email, enable email/password and **confirm email**.
3. Configure an appropriate Auth Site URL and email-confirmation redirect. Validate the email template, SMTP limits, and deliverability before inviting users. Do not disable confirmation to make testing easier.
4. In the SQL Editor, execute `supabase/migrations/20261018_viora_online_accounts.sql` **once**. This is written for a fresh Viora database, not an existing production schema. Review every statement before execution.
5. Check that the tables `public.viora_profiles` and `public.viora_playtime` have RLS on, and that `anon`/`authenticated` have **no direct table permissions**. Only authenticated RPC functions should be callable.
6. Deploy `supabase/functions/delete-viora-account/index.ts` as the `delete-viora-account` Edge Function, with authenticated JWT verification **enabled**. The function uses server-provided admin credentials and takes the account identity only from the verified JWT. Test deleting a disposable account, including cascades to the public profile and playtime tables.

## 1b. Add the Owner-only tag tools (required for the latest desktop preview)

After the first base migration succeeds, run the **second** SQL file, `supabase/migrations/20261018_owner_tags_and_audit.sql`, in the Supabase **Database** SQL Editor. Do this only once. It adds the Tester and Owner roles and carefully scoped owner-only functions for account lookup and tag assignment, plus an audit log.

**Secure Owner bootstrap:** First register your real online account, verify your email, sign in, and finish claiming your username. In Supabase → Authentication → Users, inspect the verified user's **Auth UUID** and email to make certain it is *your* account. In a separate trusted SQL Editor query, substitute that UUID:

```sql
update public.viora_profiles
set role = 'owner'
where id = '<YOUR_VERIFIED_AUTH_UUID>';
```

This is a privileged step performed in your own dashboard, **not inside Viora**. Never promote an account based solely on a claimed public username or shared screenshot. Sign out and sign in again to refresh the role. Only the Owner can open the Developer Panel, search exact usernames, and assign Member/Tester/Developer/Administrator tags. Administrator is a **visible badge**, not database ownership; the Owner role cannot be assigned from the app. Verify an ordinary account is denied calling `viora_owner_lookup` or `viora_owner_set_role` directly.

The **Global Leaderboard** button now appears directly above the account card once signed in, and the permanent numeric User ID displays under the account name. All account tags and IDs come from server responses.

## 1c. Install Leaderboard v2 (required for the new podium build)

**Do not rerun the original accounts migration or the Owner-tags migration.**
Open the Supabase **Database** SQL Editor, clear any previously pasted SQL, and run only:
`supabase/migrations/20261018_leaderboard_v2.sql`. Expect **Success. No rows returned**.
This adds consent tracking, an authenticated Top 100 RPC, a separate accurate personal-rank RPC, and a
public Storage bucket `viora-avatars` restricted to owner-uploaded small PNG files.
Avatar filenames use public User IDs, not private authentication UUIDs. Storage RLS policies stop
users changing someone else's avatar.

**Privacy:** The public leaderboard stays **opt-in**, including for new accounts. Existing opt-in
choices remain unchanged. New users are offered a clear yes/no choice, with a saved refusal.
Avatars are independent optional uploads. The upload confirmation warns that public image URLs
may be accessed even after opting out of the leaderboard. Uploaded images are stripped of
metadata and re-encoded as at most 192-pixel PNGs (max 256 KiB). Removing a picture uses the
Storage API to delete image bytes, then server-side invalidates the public avatar version.
Caches may retain a copy temporarily. For privacy reasons, the user should never upload a
sensitive or identifying photo if they do not want it displayed publicly.

**Test:** With only one opted-in user, place #1 appears in the middle and the other
podiums show honest empty states. With 3+ opted-in test accounts, #2 appears on the left,
#1 is tallest in the centre and #3 on the right. Rankings #4–#100 appear underneath
as scrolling rows. Your own rank displays separately even if outside the Top 100; opting
out removes you from public rankings without deleting your account or local statistics.
Test initials fallback, sanitized avatar upload, replacement and explicit removal.

**Account deletion update:** Deploy the current
`supabase/functions/delete-viora-account/index.ts` with JWT verification enabled
before public distribution. It must delete any public avatar bytes through Supabase
Storage *before* deleting the authenticated account, so no public image is orphaned.
The Edge Function still requires live tests on a disposable user account and must
never be given a service-role key from the Windows client.

## 2. Connect the Windows build safely

1. In the Supabase project's Connect or Project Settings → API page, copy the **Project URL** (`https://<project-ref>.supabase.co`) and the **publishable** (`sb_publishable_...`) API key.
2. In GitHub → `balcony3232/Viora` → Settings → Secrets and variables → Actions → **Variables**, add:
   - `VIORA_SUPABASE_URL`: the project URL.
   - `VIORA_SUPABASE_PUBLISHABLE_KEY`: the public publishable key.
3. A new GitHub Actions build for the online accounts branch embeds only these public, non-privileged values as a resource. The executable does **not** contain a secret or a service-role key. An offline preview is produced if variables are absent; tagged release builds are blocked until configured.
   After saving both variables, run a **fresh** Windows build on `feature/v1.4-online-accounts-supabase`. Older downloaded EXEs are still offline-only. In the `Configure optional Viora Online backend` step, confirm the log says `Viora Online public project configuration embedded.` (never print the key). Download only the artifact from that successful new run.
4. For local development only, you can create `Assets/OnlineConfig.json` containing two JSON string fields `supabaseUrl` and `publishableKey`. This file is gitignored and must not contain passwords or secret keys.

**Never paste or commit a `service_role`, `sb_secret_`, database connection string, JWT signing secret, email provider credential, or users' passwords.** Publishable keys are intentionally public and must be restricted by permissions.

## 3. Verify account and role behaviour

- Create two accounts with distinct verified emails. Claim `TestUser` on account A. Account B attempting `testuser` must receive a conflict and be able to pick a new name. Two near-simultaneous claims must result in exactly one winner.
- Confirm that registering but **not verifying** an email does not reserve a username.
- Each claimed user has a stable `public_id`, starting with `1`; the UI renders the number padded to six digits. The underlying authenticated identity is Supabase Auth UUID and never exposed on the leaderboard.
- Sign in on another PC using email and password: same username, public ID and server-managed role; FastFlag profiles, custom themes and local playtime remain PC-local. Existing v1.3 legacy local accounts still work in the separate offline option.
- Test incorrect password, expired access token refresh, lost network, sign-out and email confirmation failures. Neither access nor refresh tokens should be saved to disk.
- To mark a verified developer manually, obtain **their actual UUID from Authentication → Users** (not their username) and run in the trusted SQL Editor only:

```sql
update public.viora_profiles
set role = 'developer'
where id = '<verified-auth-user-uuid>';
```

- Test that an authenticated user cannot change their own role, another username, any `public_id`, or anyone else's playtime via REST or direct SQL API; they must also be unable to enumerate emails.
- The UI renders `developer` and `administrator` badges from server-provided data only. No user-controlled flag, profile file or Auth metadata confers a role.

## 4. Playtime and privacy verification

- Players are **not listed by default**. They must explicitly check the leaderboard opt-in.
- While opted out, online time must not be uploaded or credited. Local session measurement continues as before.
- While opted in, Viora sends a boolean Roblox-running signal approximately every 60 seconds, and the database estimates time using server timestamps. A new interval requires consecutive playing pings 20–95 seconds apart, credit capped at 65 seconds per ping. This reduces accidental clock manipulation but **does not prevent a modified client from faking activity**. Don't distribute ranked prizes, account privileges, or valuable rewards based on this number.
- Leaderboard v2 returns up to 100 opted-in profiles and a separate personal rank even outside the visible Top 100. A player's opt-out removes their public row when rankings are refreshed; previously credited seconds remain stored privately until deletion/reset support is in place.
- Old local playtime is **not** imported or copied to the server automatically.
- Account deletion is implemented as a confirmed call to an authenticated server-side Edge Function, but remains **untested until deployed**. Password recovery, moderation/abuse controls, email-delivery capacity and a full privacy notice must be validated before public release. Password recovery is not yet available in the preview UI.
